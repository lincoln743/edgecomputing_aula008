Interrupções linha a linha

O sketch do ESP32 que conta cliques por interrupção de hardware, trata o repique do botão e comanda um LED RGB pela porta serial — explicado instrução por instrução.

ESP32 DevKit Push button · GPIO 15 LED RGB · 25 / 26 / 27 Buzzer · GPIO 23 115200 bps

O que acontece quando você aperta o botão

Sem interrupção, o programa precisa perguntar o tempo todo se o botão mudou — e pode perder um clique curto entre duas perguntas. Com interrupção, o próprio hardware avisa. Esta é a sequência, nesta ordem:

  1. Etapa 1

    Borda

    O pino vai de 3,3 V para 0 V no instante do clique. É a borda de descida (FALLING).

  2. Etapa 2

    Desvio

    A CPU pausa o loop() exatamente onde estava e guarda o ponto de retorno.

  3. Etapa 3

    ISR

    Executa isrBotao(): debounce, incrementa o contador, levanta a flag. Microssegundos.

  4. Etapa 4

    Retorno

    Volta para o loop() na instrução seguinte. O loop vê a flag e faz o trabalho pesado.

A regra que organiza tudo: a ISR registra o evento, o loop() reage a ele. Imprimir na serial dentro de uma ISR é o erro clássico — Serial.print() é lento e depende de interrupções que estão desabilitadas enquanto a ISR roda.

1 · Pinos e constantes

// FIAP - Edge Computing - Aula 08
#include <Arduino.h>

const int BTN = 15;
const int R   = 25;
const int G   = 26;
const int B   = 27;
const int BUZ = 23;
const int CANAL_BUZ = 0;
#include <Arduino.h>

Traz as funções básicas (pinMode, digitalWrite, millis). No editor do Wokwi ela é implícita, mas deixar explícito faz o mesmo arquivo compilar também no PlatformIO.

const int BTN = 15;

Número do GPIO do botão. const permite ao compilador substituir o valor direto na instrução — não gasta RAM e evita que uma linha distraída mude o pino no meio do programa.

const int R = 25; const int G = 26; const int B = 27;

Um GPIO por canal do LED RGB. Todo o resto do código fala em R, G e B: para mudar a montagem, você edita só estas três linhas.

const int BUZ = 23;

Buzzer. É opcional no circuito — se não ligar nada aqui, o tone() do loop simplesmente não produz som e o resto continua funcionando.

const int CANAL_BUZ = 0;

O buzzer não toca com digitalWrite: ele precisa de uma onda quadrada, e quem a gera no ESP32 é o periférico LEDC (o mesmo que faz PWM). O tone() usa o canal 0 por padrão; esta constante dá nome a esse número para o setup() poder configurá-lo antes do primeiro tom.

2 · As variáveis que a ISR compartilha com o loop

volatile unsigned long contador = 0;
volatile unsigned long ultimo   = 0;
volatile bool          clique   = false;

const unsigned long DEBOUNCE_MS = 200;
const unsigned long BLINK_MS    = 250;
volatile unsigned long contador = 0;

volatile é a palavra que faz este programa funcionar. Ela avisa o compilador: esta variável muda fora do fluxo normal. Sem ela, o otimizador lê contador uma vez, guarda numa posição de registrador e reusa o valor velho — o contador parece travado em zero mesmo com a ISR incrementando.

volatile unsigned long ultimo = 0;

Guarda o instante (em milissegundos desde o boot) do último clique aceito. É a memória do debounce.

volatile bool clique = false;

A flag. A ISR só levanta a bandeira; quem olha para ela e age é o loop(). Esse é o contrato que mantém a ISR curta.

const unsigned long DEBOUNCE_MS = 200;

Janela morta após um clique válido. O contato metálico do botão abre e fecha várias vezes em poucos milissegundos ao ser pressionado — sem essa janela, um clique vira cinco.

const unsigned long BLINK_MS = 250;

Meio período do modo BLINK: 250 ms aceso, 250 ms apagado, ou seja, duas piscadas por segundo.

3 · A ISR

void IRAM_ATTR isrBotao() {
  unsigned long agora = millis();
  if (agora - ultimo > DEBOUNCE_MS) {
    contador++;
    clique = true;
    ultimo = agora;
  }
}
void IRAM_ATTR isrBotao() {

IRAM_ATTR manda o compilador colocar esta função na RAM interna do ESP32, em vez da memória flash. O motivo é concreto: quando a flash está ocupada (uma escrita, uma leitura de arquivo), uma função que morasse lá não poderia ser chamada, e a interrupção travaria o chip.

unsigned long agora = millis();

Carimbo de tempo do evento. Uma variável local não precisa de volatile — ela existe só durante esta chamada.

if (agora - ultimo > DEBOUNCE_MS) {

O debounce inteiro está aqui: só aceita o clique se passaram mais de 200 ms desde o anterior. A subtração entre unsigned long continua correta mesmo quando millis() estoura e volta a zero, depois de 49 dias ligado.

contador++; clique = true; ultimo = agora;

As três únicas ações da ISR: conta, sinaliza, anota a hora. Nada de Serial, nada de delay(), nada de tone(). Toda a rotina termina em microssegundos.

Por que a ordem importa: ultimo = agora vem depois de contar. Se você atualizasse ultimo antes do if, cada repique reiniciaria a janela e o clique nunca seria aceito.

4 · Acender as cores

void setRGB(bool r, bool g, bool b) {
  digitalWrite(R, r);
  digitalWrite(G, g);
  digitalWrite(B, b);
}

bool aplicarCor(const String& c) {
  if      (c == "R")   setRGB(1, 0, 0);
  else if (c == "Y")   setRGB(1, 1, 0);
  // ... G, B, M, C, W, OFF
  else return false;
  return true;
}
digitalWrite(R, r);

Sem ! na frente. O LED do circuito é de cátodo comum: o terminal comum vai ao GND, então nível ALTO acende o canal. Num LED de ânodo comum (comum no 3V3) a lógica inverte e a linha vira digitalWrite(R, !r).

setRGB(1, 1, 0);

As cores secundárias saem de acender dois canais juntos: vermelho + verde = amarelo, vermelho + azul = magenta, verde + azul = ciano, os três = branco.

bool aplicarCor(const String& c)

Devolve true quando reconheceu o comando. É isso que permite ao loop() distinguir "cor aplicada" de "comando desconhecido" sem repetir a lista de cores em dois lugares. O const String& passa a string por referência, sem copiá-la.

Divergência na apostila

O material lista o LED como cátodo comum no circuito, mas o trecho de código usa digitalWrite(R, !r) com o comentário "ânodo comum". As duas coisas juntas fazem o LED acender invertido — cor apagada quando deveria acender. Este código usa cátodo comum, de ponta a ponta.

5 · setup()

void setup() {
  Serial.begin(115200);
  delay(1000);

  pinMode(BTN, INPUT_PULLUP);
  pinMode(R, OUTPUT); pinMode(G, OUTPUT); pinMode(B, OUTPUT);
  pinMode(BUZ, OUTPUT);
  setRGB(0, 0, 0);

  ledcSetup(CANAL_BUZ, 2000, 10);
  ledcAttachPin(BUZ, CANAL_BUZ);

  attachInterrupt(digitalPinToInterrupt(BTN), isrBotao, FALLING);
}
Serial.begin(115200);

Abre a porta serial nessa velocidade. O Serial Monitor precisa estar no mesmo valor — em outra velocidade você vê caracteres embaralhados, não linhas vazias.

delay(1000);

Um segundo de espera antes da primeira impressão. O Serial Monitor do Wokwi leva um instante para se conectar e, sem isso, o cabeçalho do programa se perde.

pinMode(BTN, INPUT_PULLUP);

Liga o resistor de pull-up que existe dentro do próprio ESP32. Em repouso o pino fica preso em HIGH; apertar o botão o conecta ao GND e ele cai para LOW. Sem o pull-up o pino ficaria flutuando e dispararia interrupções sozinho, por ruído.

pinMode(R, OUTPUT); ...

Os três canais do LED e o buzzer viram saídas. Um pino que ficou como entrada não acende nada, e o erro é silencioso.

setRGB(0, 0, 0);

Estado inicial definido. Logo após o boot o nível dos pinos é indefinido; esta linha garante que o programa começa com o LED apagado, coerente com modo = "OFF".

ledcSetup(CANAL_BUZ, 2000, 10); ledcAttachPin(BUZ, CANAL_BUZ);

Cria o canal LEDC antes do primeiro tone(). Sem estas duas linhas, o primeiro bipe imprime E ledc: ledc_get_duty(745): LEDC is not initialized no Serial Monitor: no core Arduino-ESP32 2.0.x o tone() prende o pino ao canal antes de configurar o driver, e essa leitura de duty falha porque o periférico ainda não foi inicializado. O som sai igual — quem perde é a leitura do monitor serial. O ledcSetup(0, 2000, 10) configura o canal 0 com 2 kHz e 10 bits de resolução, e cada tone() reajusta a frequência do bipe.

attachInterrupt( digitalPinToInterrupt(BTN), isrBotao, FALLING);

A linha que arma tudo, com três argumentos. digitalPinToInterrupt(BTN) traduz o número do GPIO para o número do canal de interrupção. isrBotao é o nome da função, sem parênteses — você está passando a função, não chamando. FALLING escolhe a borda: com pull-up, apertar é a descida. RISING dispararia ao soltar e CHANGE nos dois, contando o dobro.

6 · loop(), parte 1 — o clique

if (clique) {
  clique = false;

  noInterrupts();
  unsigned long total = contador;
  interrupts();

  Serial.print(F("Cliques: "));
  Serial.println(total);
  tone(BUZ, 1500, 80);
}
if (clique) {

O loop passa por aqui milhares de vezes por segundo e quase sempre encontra false — custa uma comparação. Só quando a ISR levantou a flag é que há trabalho.

clique = false;

Consome o evento logo na entrada. Se você zerasse a flag no fim do bloco, um clique chegando durante a impressão seria apagado junto e você perderia a contagem na tela.

noInterrupts(); unsigned long total = contador; interrupts();

Leitura atômica. contador tem 32 bits e a ISR pode alterá-lo no meio da cópia, produzindo um valor que nunca existiu. Desligar as interrupções por três instruções resolve — e religá-las imediatamente é obrigatório, senão o botão para de funcionar.

Serial.print(F("Cliques: "));

O F() mantém o texto literal na flash em vez de copiá-lo para a RAM no boot. Num programa pequeno é detalhe; num projeto grande, é a diferença entre caber e não caber na memória.

tone(BUZ, 1500, 80);

1500 Hz por 80 ms. O terceiro argumento é a duração: o tom se desliga sozinho e o loop segue na mesma volta. Com tone(BUZ, 1500) sem duração, você precisaria de um noTone() depois.

7 · loop(), parte 2 — os comandos

if (Serial.available()) {
  String c = Serial.readStringUntil('\n');
  c.trim();
  c.toUpperCase();

  if (c == "RESET") {
    noInterrupts(); contador = 0; ultimo = 0; interrupts();
    Serial.println(F("contador zerado"));
  } else if (c == "BLINK") {
    modo = "BLINK";
    ultimoBlink = millis();
    blinkAceso  = false;
  } else if (aplicarCor(c)) {
    modo = c;
  } else {
    Serial.println("comando desconhecido: " + c);
  }
}
if (Serial.available()) {

Verdadeiro quando há pelo menos um byte esperando no buffer de recepção. Sem essa checagem, a leitura seguinte bloquearia o programa esperando alguém digitar.

String c = Serial.readStringUntil('\n');

Lê até o Enter. Por isso o comando só surte efeito quando você tecla Enter no Serial Monitor — digitar as letras não basta.

c.trim();

Remove espaços e, principalmente, o \r que vem antes do \n em alguns terminais. Sem isso a comparação c == "R" falha contra o texto "R\r" e nenhum comando funciona — é o bug mais comum deste exercício.

c.toUpperCase();

Faz off, Off e OFF valerem a mesma coisa.

noInterrupts(); contador = 0; ...

Mesma proteção da leitura, agora na escrita: zerar um valor de 32 bits não é uma operação única para o processador, e um clique no meio deixaria o contador num estado incoerente. ultimo = 0 também é zerado para o próximo clique não cair na janela de debounce antiga.

} else if (aplicarCor(c)) {

A chamada faz duas coisas ao mesmo tempo: aplica a cor e responde se o comando existia. Quando devolve false, o else final avisa o usuário em vez de ignorar o que ele digitou.

modo = c;

Escolher uma cor tira o LED do modo BLINK, porque a condição do piscar testa modo == "BLINK". Um único if/else if encadeado garante que só um ramo executa por comando.

O que estava quebrado na versão da apostila

Lá, depois do else if (c == "BLINK") modo = "BLINK";, vinha uma linha solta: if (c != "BLINK") modo = c;. Como ela roda fora da cadeia, qualquer texto digitado — inclusive um erro de digitação — virava o modo atual. Aqui a atribuição de modo acontece dentro de cada ramo.

8 · loop(), parte 3 — piscar sem travar

if (modo == "BLINK" && millis() - ultimoBlink >= BLINK_MS) {
  ultimoBlink = millis();
  blinkAceso  = !blinkAceso;
  setRGB(blinkAceso, blinkAceso, blinkAceso);
}
millis() - ultimoBlink >= BLINK_MS

Compara tempo decorrido em vez de parar o programa. É a diferença entre "já passaram 250 ms?" e "fique parado 250 ms" — a primeira pergunta deixa o loop livre para atender a serial e o botão.

blinkAceso = !blinkAceso;

Inverte a fase a cada vencimento. Duas trocas formam um ciclo completo de 500 ms.

setRGB(blinkAceso, blinkAceso, blinkAceso);

Os três canais recebem o mesmo valor: branco piscando. Trocar por setRGB(blinkAceso, 0, 0) faz um pisca-pisca vermelho.

Por que não usar delay()

A versão original fazia setRGB(1,1,1); delay(250); setRGB(0,0,0); delay(250);. Durante esses 500 ms o loop não lê a serial: os comandos parecem ignorados e só são atendidos na volta seguinte. O clique do botão continua sendo contado — é justamente esse o mérito da interrupção — mas a mensagem no Serial Monitor chega atrasada.

Comandos no Serial Monitor

Digite e tecle Enter, com o monitor em 115200 bps.

  • R vermelho
  • G verde
  • B azul
  • Y amarelo (R+G)
  • M magenta (R+B)
  • C ciano (G+B)
  • W branco
  • OFF apaga
  • BLINK pisca branco
  • RESET zera o contador
  • STATUS contador e modo
Se o monitor ficar mudo: no Wokwi do VS Code a simulação pausa quando a aba do simulador não está visível — e aí o Serial Monitor para de receber e de enviar. O sintoma é justamente esse: o painel abre, nada aparece e nada responde ao que você digita. Volte com F1 → Wokwi: Restart Simulation (ou Wokwi: Resume Simulation) e mantenha a aba da simulação à vista. Digite os comandos no painel que fica dentro da própria aba da simulação: é o único monitor que não tira a aba de vista. Para um monitor externo, use o terminal do painel inferior (View → Terminal) com pio device monitor -p rfc2217://localhost:4000 -b 115200, a porta virtual definida no wokwi.toml. Evite abrir o monitor como aba de editor: ele esconde a aba da simulação e o simulador pausa de novo.
